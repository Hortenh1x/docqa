# RFC-05: Tenant isolation model

## 1. Context

Kranich Route Cloud serves logistics operators of varying sizes. Each customer operates in its own tenant, and tenants must never observe each other's routes, stops, vehicle data, or configuration. As our customer base grows, we need an explicit, documented isolation model that engineers can apply consistently when building new services.

Today, isolation is enforced mostly by convention. Each service uses its own database schema, and developers are expected to include tenant identifiers in every query. This has worked reasonably well, but it leaves room for error. A missing filter clause in one query can leak data across tenants. We have also seen cases where shared infrastructure, such as background job queues, briefly mixed metadata from different tenants.

This RFC proposes a tenant isolation model that we can implement across the Platform & Infrastructure team and recommend to the other product teams. The model is meant to be practical: it should not require a rewrite of existing services, but it should give us a clear target for new work and for hardening existing components over time.

## 2. Proposal

We adopt a defense-in-depth approach with three layers.

First, every service must derive the tenant context from an authenticated request. Tenant identifiers are never taken from request bodies or URL parameters alone. The API gateway injects a verified tenant claim into each request after authentication, and services must use that claim as the source of truth for data access.

Second, every persistence layer must enforce tenant scoping at the query level. We standardize on a shared data-access library that automatically appends tenant predicates to queries generated by our ORM. Direct SQL is allowed only when the query passes through the same library or when a code review explicitly confirms tenant scoping.

Third, operational boundaries must separate tenants at the infrastructure level where feasible. We will move toward per-tenant schemas in our primary relational store and keep shared schemas only for reference data that is genuinely global, such as country codes or unit definitions.

The model applies to all environments, including staging and development. Test tenants are real tenants from the model's perspective, with the same guarantees.

## 3. Details

### 3.1 Tenant context propagation

The API gateway authenticates every request and resolves the caller to a tenant. It then forwards a signed header containing the tenant identifier. Services must not accept tenant identifiers from client-supplied headers. If a service receives a request without the gateway header, it rejects the request.

Background jobs and event consumers must carry tenant context explicitly. When a service enqueues a job, it includes the tenant identifier in the job payload. When a consumer processes the job, it reconstructs the tenant context before touching any data. We will extend our internal event library to require a tenant field on all domain events.

Example: Anna, a backend engineer in Lisbon, adds a new background task that recalculates route distances. She includes the tenant identifier in the task payload and verifies that the consumer sets the tenant context before calling the data-access layer.

### 3.2 Data-access rules

All services use the shared data-access library for persistence. The library supports two modes:

- Schema-scoped mode: the library connects to a tenant-specific schema and does not allow cross-schema references.
- Row-scoped mode: the library appends a tenant predicate to every query and validates that all write operations include the tenant identifier.

New services must use schema-scoped mode. Existing services may continue in row-scoped mode while they migrate, but the migration backlog is tracked by the Platform & Infrastructure team.

Direct SQL is permitted in two cases only. First, for read-only queries that the data-access library cannot express, provided the query is reviewed by another engineer who verifies the tenant predicate. Second, for migrations and maintenance scripts that run outside the request path and operate on a single tenant at a time.

### 3.3 Operational isolation

In the primary relational store, each tenant gets its own schema. Schemas are created through a provisioning process that also sets up the tenant's service accounts. Cross-tenant joins are forbidden at the database level; where reporting requires aggregated data across tenants, we use a separate analytics pipeline that copies data into a warehouse with its own access controls.

Object storage follows the same pattern. Each tenant has a dedicated prefix, and access policies restrict service accounts to their own prefix. We will add a linting step to our infrastructure-as-code repository to catch misconfigured policies before they reach production.

Caching layers must include the tenant identifier in the cache key. No cache entry may be readable by more than one tenant. Where a cache is shared, the key namespace must be tenant-specific and the cache must be treated as untrusted, meaning services validate authorization after a cache hit.

### 3.4 Testing and verification

Each service must include tests that attempt to access another tenant's data. These negative tests are part of the definition of done for any feature that reads or writes customer data. The Platform & Infrastructure team maintains a shared test fixture with two synthetic tenants that engineers can use for this purpose.

We also run periodic automated scans that probe for common isolation failures, such as missing predicates or overly broad cache keys. Findings are triaged with the same severity as other security defects.

## 4. Alternatives considered

We considered a shared-schema model with row-level security enforced by the database. This approach reduces provisioning overhead and makes cross-tenant queries easier. We rejected it as the primary model because row-level security can be accidentally disabled by a misconfigured migration, and it is harder to reason about when services use raw SQL.

We also considered hard multi-tenancy with a separate database instance per tenant. This gives the strongest isolation but does not scale operationally for our customer base. Provisioning, backups, and connection management would become a bottleneck, and our smaller customers do not need that level of separation.

Finally, we discussed using a middleware layer that rewrites queries automatically without requiring services to use the shared library. This was rejected because query rewriting is fragile and hard to debug. We prefer explicit tenant context over implicit magic.

## 5. Rollout

The rollout happens in three waves, each with its own exit criteria.

In the first wave, we introduce the shared data-access library and the tenant-context header. The Platform & Infrastructure team adopts both in its own services. We document the model on Grove and record a short walkthrough for engineers.

In the second wave, Routing Core and Fleet Insights adopt the library for all new code. Existing row-scoped services remain functional, but any change to a data-access path must pass through the new library. The Platform & Infrastructure team reviews the migration backlog with each engineering manager.

In the third wave, we enable the automated isolation scans and require negative tenant tests for all services that store customer data. We also complete the object-storage policy linting step. The rollout is complete when every service in production passes the scans and has negative tests in its test suite.

Throughout the rollout, the Platform & Infrastructure team hosts a monthly office hour where engineers can ask questions about the model. Deniz and Marek have also offered to share customer-facing examples of isolation requirements, so that engineers understand why this matters for our customers' trust.

## 6. Open questions

We have not yet decided how to handle tenants that need to share data with a partner, for example when two logistics operators collaborate on a joint route. The current model forbids cross-tenant access entirely. We need a separate mechanism for explicit, audited data sharing, and we will address that in a follow-up RFC.

We also need to clarify how the model applies to our internal tooling. Perch and Ledgerly, for example, store data about employees rather than customers. The isolation model in this RFC is scoped to customer data, but we should confirm that internal tools have their own access controls.

Finally, we should revisit the model when we introduce new storage technologies, such as a document store or a search index. The principles in this RFC should carry over, but the implementation details will differ, and we want to document those differences as they arise.
